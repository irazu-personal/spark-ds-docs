Accessibility

Spark is built to meet WCAG 2.1 AA standards. This page covers the system-wide approach to focus management, color contrast, keyboard navigation, and motion.

Standards

All components in Spark target WCAG 2.1 Level AA conformance. This means:

Perceivable

  • Text contrast ratio of at least 4.5:1 for normal text and 3:1 for large text
  • Non-text elements (icons, borders, focus rings) maintain at least 3:1 contrast against adjacent colors
  • Color is never the sole means of conveying information
  • All images and icons include appropriate alt text or aria-labels

Operable

  • All interactive elements are reachable and operable via keyboard
  • Focus order follows a logical reading sequence
  • No keyboard traps exist within components
  • Skip navigation links are provided on every page

Understandable

  • Language attribute is set on the HTML element
  • Form inputs have visible labels and clear error messages
  • Navigation is consistent across pages
  • Error identification provides specific descriptions, not just color changes

Robust

  • Valid, semantic HTML is used throughout
  • ARIA attributes are applied where native semantics are insufficient
  • Components are tested with screen readers (VoiceOver, NVDA)

Focus States

Every interactive element in Spark has a visible focus indicator. The system uses a consistent focus ring approach:

Focus Ring Tokens

  • --semantic-action-primary-border-focus provides the default focus ring color for form controls and action elements
  • --semantic-button-border-focus provides the focus ring color for all button variants
  • Focus rings use a 2px solid outline with a 2px offset to ensure visibility against all backgrounds
  • Focus rings appear only on keyboard navigation (:focus-visible), not on mouse click

Focus Management Rules

  • Modals and drawers trap focus within the dialog while open
  • When a modal closes, focus returns to the element that triggered it
  • Dropdown menus move focus to the first item on open, and return focus on close
  • Tab order follows the visual layout, top-to-bottom and left-to-right

Color Contrast

The Spark token system is designed so that standard token pairings automatically meet contrast requirements.

Built-in Contrast Pairings

  • --semantic-content-primary on --semantic-surface-white provides 15.4:1 contrast
  • --semantic-content-secondary on --semantic-surface-white meets the 4.5:1 minimum
  • --semantic-content-inverse on --semantic-surface-inverse provides high contrast for dark surfaces
  • Feedback colors (critical, success, warning, info) are tested against their corresponding surface tokens

Guidelines for Custom Usage

  • Always pair content tokens with their intended surface tokens
  • Do not use --semantic-content-tertiary for essential information as it has reduced contrast
  • Test custom color combinations with a contrast checker before shipping
  • Disabled states are exempt from contrast requirements per WCAG but should still be distinguishable

Keyboard Navigation

Spark components support standard keyboard interaction patterns.

Key Behavior Components
Tab Move focus to the next focusable element All interactive elements
Shift + Tab Move focus to the previous focusable element All interactive elements
Enter Activate buttons, follow links, submit forms Button, Link, Input
Space Toggle checkboxes, activate buttons, select options Checkbox, Button, Radio, Toggle
Arrow Keys Navigate within composite widgets Tabs, Radio Group, Dropdown Menu, Slider
Escape Close overlays and cancel actions Modal, Dropdown, Drawer, Popover, Toast
Home / End Jump to first or last item in a list Tabs, Dropdown Menu, Table

Motion and Animation

Spark respects user motion preferences and keeps animations minimal.

Principles

  • All animations respect the prefers-reduced-motion media query
  • When reduced motion is preferred, transitions are replaced with instant state changes
  • No animation exceeds 400ms duration
  • Animations serve a functional purpose (indicating state change, guiding attention) rather than decoration
  • No content relies solely on animation to be understood

Implementation

  • Use CSS transition for state changes (hover, focus, active)
  • Wrap all motion in @media (prefers-reduced-motion: no-preference)
  • Provide an immediate fallback for users who prefer reduced motion

Screen Reader Support

ARIA Usage Guidelines

  • Prefer native HTML elements over ARIA (a <button> over role="button")
  • Use aria-label or aria-labelledby when visible text is insufficient
  • Apply aria-expanded to toggles that reveal/hide content
  • Use aria-live regions for dynamic content updates (toast notifications, form validation)
  • Mark decorative icons with aria-hidden="true"
  • Group related form fields with <fieldset> and <legend>
